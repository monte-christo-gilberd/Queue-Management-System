# Architecture Summary — Queue Management System

Updated on 17 November 2026 to match the code: five services (backend, auth, notify, mail, payment), an email outbox, the public display, QRIS payments through BorderPay, and email verification. Joining uses a 6-character code generated by the backend (the qr-service has been removed). Login was split out into `auth-service` (phase 1) and Google login was added (phase 2).

## Big picture

```
   Phone / browser
        │  HTTP (LAN) or HTTPS (Cloudflare tunnel)
        ▼
 ┌──────────────┐   the only port exposed to the host (8080; prod only 127.0.0.1)
 │    nginx     │   rate limits for login, /join, password reset, avatar, payments; unbuffered SSE
 └──┬────┬────┬─┘
    │    │    │ /internal/ → always 404
    │    │    └──────────────► frontend (Expo web; Metro in dev, static in prod)
    │    ├── /api/ ──────────► backend (Go, Gin) ──► PostgreSQL
    │    ├── /api/v1/webhooks/borderpay ► payment-service ──► PostgreSQL (role payment_rw) + BorderPay
    │    └── login, register, google, reset password, email verification ► auth-service ──► PostgreSQL (role auth_rw)
    │                              │   └──► mail-service (password reset and verification emails; internal only)
    │                              (issues RS256 JWTs; the backend verifies them locally, without calling it)
    │    backend ─ /internal/v1/payments (X-Service-Token) ─► payment-service (subscription checkout)

 PostgreSQL ─ pg_notify('queue_events') ─► notify-service ─► Web Push (browser) and FCM (Android app)
 PostgreSQL ─ notification_outbox       ─► mail-service   ─► SMTP (Mailpit in dev)
    internal Docker network: db, backend, notify, mail, payment, auth, frontend expose no ports
```

Five Go services, one database, one frontend, one proxy (dev also runs Mailpit). Only nginx connects to the outside. The supporting services cannot be reached from outside, except `payment-service` (only the webhook `/api/v1/webhooks/borderpay`) and `auth-service` (only the `/api/v1/users/...` paths for login, register, password reset, and email verification). `auth-service` is separate from the queue: the backend does not call it and the reverse is also true (enforced by `scripts/check-service-isolation.sh`). The backend only calls `payment-service` for subscription checkout (`internal/paymentclient`, timeout `PAYMENT_HTTP_TIMEOUT`, default 20 seconds).

## 1. Database (PostgreSQL)

16 tables in `db/migrations/`: `users`, `owners`, `payments`, `payment_orders`, `queues`, `queue_settings`, `counters`, `tickets`, `ticket_notes`, `queue_history`, `push_subscriptions`, `push_devices` (FCM tokens of the Android app), `user_avatars`, `notification_outbox`, `user_action_tokens`, `queue_displays`. The per-service roles are created by the scripts `03_notify_role.sh`, `04_mail_role.sh`, `06_auth_role.sh`, `07_metrics_role.sh`, and `08_payment_role.sh`; `payments` and `payment_orders` are written by payment-service.

| Decision | Reason |
|---|---|
| Gap-based `sort_key`, not sequential positions | A requeue only needs to write one row |
| A customer's position is computed, not stored | Avoids manual synchronization and race conditions |
| A new ticket's sort key = max of all tickets + 65536 | `UNIQUE (queue_id, sort_key)` also covers completed tickets. Computing from `waiting` tickets only collides once a queue is drained (the 503 bug of week 14) |
| Customers must log in (`tickets.user_id`) | Account-based duplicate-join protection: the partial unique index `(queue_id, user_id)` only covers `waiting` and `currently_served`, so after completion or cancellation a user may join again and receive a new number |
| One default counter per queue (`is_default`), plus custom counters (at most 10 per queue) | Simplifies the model after the admin system was removed. One account can be used on several devices, each device serving one counter |
| `queues.ticket_prefix` (1–3 letters or digits, default `A`) | Display only: the ticket label `A2`. The `sort_key` and the ticket number do not change. Also returned by `/users/me/tickets` |
| No permanent deletion, no history limit, no daily QR limit, no `registration_limit` | Product decision of 31 October |
| Profile photo in the `user_avatars` table (BYTEA, at most 150 KB, private) | Included in the database backup; the path to object storage goes through `service.AvatarStore` |
| Password reset and email verification tokens in `user_action_tokens` (SHA-256 hashes only) | One table for `password_reset`, `email_verify`, and `email_change` (the last is not used yet); `users.password_changed_at` revokes old sessions |
| Ticket emails through `notification_outbox` (a trigger, in the same transaction as the ticket change) | Emails are not lost when SMTP or mail-service is down |
| Public display: `queue_displays` with a random token in the URL | No login; `notify_ro` and `mail_rw` have no privileges on this table |
| `owners.subscription_expires_at`, not a boolean | "Active" is computed, no cron job needed |
| `ON DELETE CASCADE` on the child foreign keys of `queues` | Deleting a queue does not get stuck |

**Removed October 2026:** `queue_authz`, `queue_admins`, `owner_saved_admins`. The admin system was removed entirely. Only the owner manages a queue.

Additional indexes are in `02_Indexes.sql` (the owner's queue list, a customer's ticket history, completed tickets). The index on `users.username` is deferred. For table details, see [ERD.md](ERD.md) and `db/migrations/README.md`.

## 2b. notify-service (Go, separate)

Listens to `pg_notify('queue_events')` from the trigger `tickets_notify_trg`, reads data through the `notify_ro` role, and sends Web Push (VAPID) to browsers and, when `FCM_*` is set, FCM HTTP v1 to the Android app (tokens in `push_devices`; no Firebase SDK, service account credentials in `keys/fcm/`). Only the internal port 8091 is used for `GET /health` (200 when LISTEN is active; used by the Compose healthcheck, not published by nginx). There is no outbox (a push sent while the service is down is lost; email already uses an outbox, see 2c). Sending uses an 8-second timeout and 3 retries for temporary failures; JSON logs; shutdown waits for pushes in progress. The backend only provides `recall` and the `/push/*` endpoints (including `/push/fcm/register|unregister` when `FCM_PROJECT_ID` is set).

## 2c. mail-service (Go, separate)

The only email sender; internal port 8092, no nginx route. Two paths: (1) the API `POST /internal/v1/send` (`X-Service-Token`), used by auth-service for password reset, email verification, and `email-verified` emails; and (2) the outbox worker: the trigger `tickets_email_outbox` writes `notification_outbox` in the same transaction as the ticket change (joined, cancelled, removed by the owner, completed), then the worker sends through SMTP with retries and backoff, rate limiting, and `FOR UPDATE SKIP LOCKED` (at-least-once). Nine templates (`joined`, `cancelled`, `removed`, `completed`, `queue-closed`, `email-verify`, `email-verified`, `password-reset`, `test`). The database role `mail_rw` has minimal privileges. Dev uses Mailpit; prod chooses `MAIL_MODE=smtp|mailpit` (default `mailpit`). notify-service does not depend on it.

## 2e. auth-service (Go, separate)

Login, registration, Google login, forgot/reset password, and email verification (`POST /api/v1/users/{register,login,google,google/link,forgot-password,reset-password,verify-email}` and `POST /api/v1/users/me/verify-email/resend`). The paths and response shapes are the same as those the backend used to serve, so the frontend did not change; nginx routes those paths to internal port 8094. The only token issuer: an RS256 JWT (claims `sub`, `iat`, `exp` of 24 hours, header `kid`) signed with the private key `keys/auth-private.pem`, which is mounted only into this service (created by `scripts/gen-auth-keys.sh`). The database role `auth_rw` may only read and write the login columns of `users` and the `user_action_tokens` table (no `DELETE`, no access to queues or tickets). Emails are sent through mail-service (HTTP, no `depends_on`).

**Isolated from the queue.** The backend verifies tokens **locally** with the public key `keys/auth-public.pem`, and session revocation (`users.password_changed_at` newer than `iat`) is read directly from the database. The email verification guard on joining and creating a queue also reads `users.email_verified_at` from the database. So when auth-service is down, logged-in users can keep using queues, tickets, SSE, profile, and payments; new logins, registrations, password resets, and email verification get a JSON 503 `AUTH_UNAVAILABLE` from nginx (with the header `Retry-After: 30`), and the frontend does **not** log out (only a 401 ends a session). Proven by the chaos test (see section 5). Verification enforces the algorithm per key (RS256 only with the public key), rejects `alg=none`, algorithm confusion, and tokens with a `purpose` claim (a Google link token is not a session). **Google login** (optional, `GOOGLE_CLIENT_IDS`): the ID token is checked on the server against Google's JWKS; an email that is already registered with a password is never linked automatically, its owner must prove the password (a 5-minute single-use link token). There is no HS256 transition period: `JWT_LEGACY_HS256_SECRET` does not exist in the code, and all HS256 tokens are rejected. Enforced by `scripts/check-service-isolation.sh`.

## 2d. payment-service (Go, separate)

One capability: extend an owner's subscription by one month (30 days) through QRIS BorderPay. Two paths:

- Internal API `POST /internal/v1/payments` (`X-Service-Token`), called by the backend to create a `pending` order in `payment_orders` and a transaction at BorderPay, then return `pay_url` and `reference_id`.
- Public webhook `POST /api/v1/webhooks/borderpay` (through nginx, verified with the header `x-borderpay-token`). The `payment.paid` event marks the order as paid and extends `owners.subscription_expires_at` in one transaction.

The webhook is idempotent: a re-sent delivery does not apply the payment twice, and an amount that does not match the order is rejected (409). A regular user's first payment also makes them an owner. The database role is `payment_rw`. When the service is down, checkout answers 503 `PAYMENT_UNAVAILABLE`, while login, queues, and tickets keep working. Internal port 8095 (`PAYMENT_SERVICE_URL`). payment-service does not verify JWTs (the backend authenticates the user and calls it with `X-Service-Token`), uses `net/http` without Gin, and uses the standard logger (text), without JSON logs, metrics, or traces. The price comes from `SUBSCRIPTION_PRICE_IDR` in the backend (default Rp15,000).

## 3. Frontend (Expo / React Native Web)

Expo Router, NativeWind, Zustand. One codebase for web and native.

- **Routes**: `login`, `register`, `forgot-password`, `reset-password`, `join`, `ticket/[queueId]`, `display/[token]` (public), and `(user)/`: dashboard, queues, detail and `live` per queue, history, profile, `subscription`. `/` is only an entry point that forwards to `/login` (guests) or `/dashboard` (logged in).
- **The QR code is drawn in the frontend** from `join_url` using `qrcode` and `react-native-svg`. The error correction level is `L`, and the size is rounded to whole pixel multiples so that phone cameras can scan it easily.
- **Two join paths**: the in-app camera scanner (`expo-camera`) calls `POST /join {t}` directly, and the `/join?t=` page (for QR codes scanned by the phone's built-in camera) calls `GET /join/preview` and then `POST /join` after the user taps Join.
- **Real-time over SSE with `fetch`**, not `EventSource`, because the stream needs the `Authorization` header.
  - Reconnect with a backoff from 1 second up to 30 seconds.
  - Resync when the tab becomes active again, and every 45 seconds.
  - When the stream does not send a single byte for 3 seconds (this happens through the Cloudflare quick tunnel, which holds the stream), data is fetched again every 3 seconds.
- The camera in the browser needs HTTPS or `localhost`.

## 4. Deployment and development

`docker-compose.yml` for development and `docker-compose.prod.yml` for demo/production (project `qms-prod`, subnet `172.29.0.0/16`, environment from `.env.prod`, static frontend, `service_healthy` for the backend). The two cannot run at the same time (port 8080). In prod, HTTPS goes through the Cloudflare Tunnel `qms-ta` to `https://<your-domain>` (the `cloudflared` service on the host, started manually), access is restricted by WAF rules based on the WiFi IP, and the Metro `Upgrade` header is not sent. An existing database schema is updated with `db/scripts/apply_schema.sql` (idempotent). All five Go services use Go 1.27. Multi-stage Dockerfiles (`dev` and `prod`). Go uses `go run` with a manual restart (`docker compose restart backend`), and the frontend uses Metro with hot reload.

nginx follows the `template-nginx/` layout: `deploy/nginx/nginx.conf` and `server.conf`. Routes:

| Path | Destination | Notes |
|---|---|---|
| `/api/v1/queues/:id/event` | backend | SSE, unbuffered, timeout 86400 seconds |
| `/api/v1/users/login`, `/register` | auth-service | `auth_zone` 10 r/s per IP; 503 `AUTH_UNAVAILABLE` when down |
| `/api/v1/users/google[/link]`, `/verify-email`, `/me/verify-email/resend` | auth-service | `auth_zone` 10 r/s per IP |
| `/api/v1/users/forgot-password`, `/reset-password` | auth-service | `reset_zone` 1 r/s, burst 5; the `/reset-password` page is logged without its query |
| `/api/v1/users/me/avatar` | backend | Body up to 6 MB, `avatar_zone` 5 r/s |
| `/api/v1/display/:token[/event]`, `/display/:token` | backend, frontend | Public display: unbuffered SSE, token masked in logs, no Referer and no cache |
| `/api/v1/webhooks/borderpay` | payment-service | Public webhook from BorderPay (`x-borderpay-token`); no rate limit; JSON 503 when the service is down |
| `/api/v1/join`, `/join/preview` | backend | `join_zone` 10 r/s per IP |
| `/api/` | backend | |
| `/internal/` | | Always 404 |
| `/` | frontend | Includes the Metro WebSocket for hot reload |

The earlier plan (counters, history and export, the public display, cancellation, number removal, payments, forgot password, email, Google login, observability) is complete. Remaining:

- Changing the email address (`email_change`) is not built yet; the `purpose` column is prepared for it.
- k6 load tests: not yet. Observability exists as an optional overlay (OpenTelemetry, Prometheus, Loki, Tempo, Grafana, 11 alert rules that do not send notifications yet); payment-service is not covered.
- Outbox for push (Web Push and FCM), native iOS notifications, a migration runner, automatic backups, HSTS and Cloudflare Access, more than one backend instance (the SSE hub is in memory).
- The QR join on the public display (the `show_qr` column does not exist yet). Subscription plans other than 1 month.
- Cancelled (decision of 31 October): the daily QR limit and `registration_limit`.
